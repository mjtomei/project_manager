## What changes in the design

### Products and verification policies

Each plan can identify intended products, their source artifacts, acceptance criteria, and verification policy. Individual activities can override plan defaults. Start with three built-in processes and a small shared acceptance interface, using existing Markdown/YAML storage:

| Process | Unit of work | Checks and completion |
|---|---|---|
| Software | A behavior change or reusable tool, usually carried by a PR | Appropriate automated tests and selected review/QA stages; sign-off recommends acceptance and the watcher applies the plan's merge policy. |
| Analysis | An investigation or batch of small scripts producing notes, data, or candidate results | In-session sanity checks and source/provenance recording. The activity can complete with explicitly unverified results. No automatic dedicated QA session or PR per script. |
| Research verification | A claim, result, figure, argument, or other intellectual product | The chosen independent verification procedure, with findings bound to the reviewed inputs, artifacts, and criteria. Acceptance concerns that product. |

Policy answers which checks a product needs, when they run, and what a successful result licenses. Choosing a cheaper model is a separate decision. The watcher can select within the plan's policy, but cannot silently drop an acceptance requirement because a check failed or became expensive.

The initial product record needs a stable reference, owning plan, intended result, artifact/evidence references, criteria, and verification state/history. A plan's activity notes can carry the working queue; do not build a second general-purpose ticket system. Product records are optional for ordinary existing software plans. Explicit records are required when a result is presented as independently verified.

An activity may finish while its product remains unverified or contested. Committing code does not mark a claim accepted. Paper integration is another activity with the project's authorship instructions. Dependencies can require a draft artifact or an accepted finding; do not infer that every downstream task must wait for every upstream review.

Choose the process by the intended product, not the repository, file extension, or amount of code. An Omerta networking tool normally has software acceptance criteria. An economic simulation or token-mechanism investigation normally has research criteria even if it involves extensive code. The same activity can deliver a reusable simulator improvement and an economic finding, with separate acceptance records: tests of the simulator's implementation do not establish the economic model's validity. Small experimental variations can remain one analysis session rather than spawning a software QA cycle for every variant.

Replace the coarse use of project-wide `skip_qa` with resolved plan/activity policies. Preserve legacy configuration behavior for untouched projects, expose its effective policy, and explicitly configure this delivery plan and the bug-fix campaign to run their required checks. An unknown or unsupported required verifier must remain outstanding, never silently pass.

Scope Phase 11's "any code/content change returns through review and QA" rule to the applicable process. Verification records identify the input/data/method/product versions and criteria they cover. Changes to those dependencies invalidate the affected finding; unrelated edits and notes do not restart a whole study review. Preserve previous reviews as history.

### Living documents and coherence maintenance

A living document has a purpose, persistent context, source/dependency references, a maintenance policy, and the ability to initiate upkeep or raise unresolved questions. Its maintainer reasons about what needs to change for the document to remain useful: stale statements, inconsistencies, missing evidence, broken links, duplicated explanations, and material that should be consolidated or moved. Start with document-scoped activities on the existing watcher/session substrate; a permanently running agent per file is unnecessary. This is a concrete first slice of [[plan-984dfeb]], including self-maintenance, while preserving its broader negotiation design.

Use editable Markdown plus lightweight metadata or sidecars, retaining existing file paths and human edits. Track document identity, relevant sections/claims, source revisions or evidence references, related documents, last checked state, pending maintenance, and policy for applying changes. Initial onboarding should discover likely relationships from links, citations, and repeated claims, then record the useful ones; keeping docs current cannot depend on a human exhaustively declaring every relationship. Periodic coherence sweeps catch missing links and changes made outside pm.

Changes to source data, accepted results, methods, code interfaces, plan decisions, or adopted child revisions schedule maintenance for affected documents. Coalesce a batch of related changes into one activity; reconcile current text against the sources, propagate supported corrections, repair links, and record what changed and why. Preserve existing documents' purposes: a methods section, study register, README, and paper need coherent claims rather than identical prose. Readers see stale, contested, and pending-update state until reconciliation completes. A last-checked revision establishes freshness relative to those sources, not scientific validity; verification remains D6's responsibility.

Contradictory sources produce a visible question or investigation, not an invented resolution. A corrected or withdrawn finding must update or flag its downstream summaries and conclusions, including uncertainty and scope. Preserve historical result snapshots and dated digests; issue linked corrections instead of rewriting the historical record. Across repositories, distinguish latest child findings from the revision the parent has actually adopted. Maintenance must not silently advance an accepted pin.

Routine maintenance follows the document's configured policy and can run unattended. Respect author-owned passages and existing paper-integration instructions: apply permitted changes, prepare scoped patches where required, and keep pending disagreements visible without blocking unrelated work. Use stale-write detection and the existing mutation helpers to preserve concurrent edits. Bounded retries, deduplication, and change-impact tracking prevent documents repeatedly rewriting each other. A no-change sweep creates no new content churn, and housekeeping alone cannot perpetually reset the campaign's no-progress limit.

Radar consumes this maintained project context and records which revisions informed each triage. Missing/stale context triggers maintenance or a visibly provisional judgment. Relevant new findings can initiate document-maintenance activities, and changed project conclusions can trigger reconsideration of affected live Radar syntheses. D10 does not depend on Radar ingestion; D7 consumes D10 and connects those two directions. Neither requires the full Mind/Sensorium migration.

For cosmic, the first concrete chain connects S10's authoritative result/method artifacts to its study plan, the study register, project overview, and relevant paper passages. For Omerta, connect child implementation/research state to child docs and parent summaries, respecting accepted revisions. A real change must result in supported document updates or an explicit unresolved/pending correction; merely refreshing a dashboard or appending a new summary does not satisfy this requirement.

Translate backend-specific instructions through a shared pm context; retain project-authored instructions. Claude transcript and hook parsing stays inside its adapter. No new backend-specific imports in plan or product logic.
