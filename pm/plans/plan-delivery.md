# Delivery: autonomous plans, research workflows, and interchangeable sessions

Make existing projects living documents with low setup and coordination effort: agents discover and maintain their plans, artifacts and executable recipes, then use PM tools to advance the work. Demonstrate this through hands-off bug discovery and burndown in pm, an external tmux crash-reproduction and repair campaign, and adoption of `mjtomei/cosmic_ac` and the `mjtomei/omerta` repository family. Support interchangeable Claude, Codex, OMP, Grok, Muse, DeepSeek and OpenCode harnesses through a shared session interface. The main purpose of this harness coverage is to test especially open models across different harnesses for performance and cost optimization. Preserve open/local model access and clean up the code around agent-controlled execution and shared project context.

## Product commitments

- pm already provides valuable planning, continuity, and help directing human attention. Develop those workflows alongside automated qualification; qualification evaluates implementations and process choices rather than gating whether the product should exist.
- Long-term planning, reliable execution, evidence, human participation, and avoiding tool lock-in are requirements. Open/local models remain supported goals for both execution and, as capabilities improve, plan-level reasoning.
- Stronger models can handle larger units of work and more orchestration. Consolidate artificial PR boundaries and repeated scaffolding accordingly. Keep portable capabilities on the roadmap even when a closed backend supplies a convenient implementation now; document the dependency and replacement boundary.
- Humans can join, inspect, and steer ongoing work. Well-scoped mechanical PRs can run unattended; exploratory work that needs human judgment is done collaboratively in the PR implementation session. A PR waiting for that collaboration, authority or resources remains visible while independent work continues.
- Research progress includes verified findings, useful negative results, corrected claims, and resolved uncertainties. Code completion, result verification, and incorporation into a paper have distinct meanings.
- Both `cosmic_ac` and the Omerta family are required adoption outcomes. Omerta exercises a larger existing codebase, cross-repository coordination, networking deliverables, and economy/token research within the same program.
- Low-effort adoption is a product requirement: the user supplies the project and goals; agents discover existing structure, generate missing plans and recipes, and ask about consequential uncertainties as they arise. Preserve existing artifacts and working practices. Measure setup and ongoing coordination effort, not only imported record counts.
- Living documents are the organizing principle of PM itself, with custom tools for acting on shared project state.
- Living documents are a must-have: plans, study registers, methods/results documentation, project overviews, and Radar syntheses need ongoing maintenance that detects drift and reconciles affected documents with their sources. D10 supplies the initial implementation and is a hard prerequisite for the useful Radar delivery. Both adoption projects must demonstrate it on real documents.
- Existing plans retain their design history and unimplemented directions. This plan owns the near-term delivery sequence for the slices named below; it does not declare the rest implemented or obsolete.
- The auto-fix loop must use the artifact-backed regression library. Migrating the existing Claude-driven tests, automatically authoring a reusable regression when none fits, and demonstrating discovery, a fix, and fresh regression evidence are requirements for loop readiness. The new sign-off recommendations in `pr-5f4f595` depend on that authoring capability.

## What changes in the design

### One PR workflow, with human collaboration when needed

The PR is the unit of work for every tracked project: code, mechanical edits, research, exploration, plans and documents. Use the existing implementation → review → QA → sign-off flow and configured merge policy. Do not introduce separate software/analysis/research PR kinds, parallel activity lifecycles, or a new product-record system. Describe the intended result, criteria, evidence and unresolved questions in the PR, its notes and linked artifacts.

Straightforward or mechanical work can run through that flow unattended within the user's authority. When the result depends on exploratory judgment that the normal agent-only flow cannot reliably provide, the human joins the PR's implementation session and works with the agent. This is a way of using the same PR, not another process type or an automatic exemption from review. Preserve the session, drafts and open questions while it awaits human participation; a watcher must not treat that wait as a failed worker or advance it on silence. When implementation is ready, continue the same PR through the existing stages.

Review and QA assess what the PR claims to deliver. Code changes need relevant behavioral checks; an investigation needs defensible methods, sources, results and stated limitations. Tests of a simulator do not by themselves validate its scientific conclusions. D6 supplies independent research-check techniques inside existing review/QA, not a second acceptance lifecycle. A required check that has not run remains outstanding. Keep existing project/PR settings and human gates; this correction does not introduce a research-specific skip path or silently change `skip_qa`.

An ordinary PR can be scoped to exploration: investigate a question, record findings and uncertainty, recommend plan changes, and identify useful next PRs. Its reviewed output can be a report or a supported decision that no further work is warranted; it need not contain a code change or pretend an open research question is solved. Supporting scripts and experiment variants can remain within that PR rather than becoming separate PRs for each tool call. Later implementation or paper integration can be follow-up PRs when separately scoped.

Plans need not predefine every PR. A PR can already file other PRs with existing PM commands, and existing plan editing/notes record the result; no new spawning framework is required. Preserve this capability. Link proposed or filed work to its originating PR, supporting evidence and plan, reuse an existing matching entry, and add dependencies only for actual ordering constraints. Filing or recommending a PR does not itself authorize starting it. Plan edits and execution continue to follow the existing authority and manual gates.

The sign-off prompt in `pr-5f4f595` must ask: **"Given the result of this PR, does the plan need to change, and is there any new work worth proposing?"** Consider goals, assumptions, priorities, missing steps, dependencies and obsolete work. Record the proposed change and reason, link supporting findings and any existing/follow-up PRs, and allow an explicit "no justified change or new work" answer. Distinguish a prerequisite needed for this PR's acceptance from optional subsequent work. Use existing plan/PR operations for authorized changes; the addition is prompt/report guidance, not new PR-creation functionality. The user's whole-prompt review remains required.

Evidence identifies the revisions, inputs, methods and criteria it covers. Relevant changes require the affected review/QA evidence to be refreshed; unrelated notes do not restart a whole investigation. Preserve previous reviews as history. Acceptance of a scoped exploration report does not certify every hypothesis mentioned in it.

Link authoritative artifacts in place, reconcile duplicate or stale plans, record uncertainty, and infer useful relationships without requiring the user to supply a complete inventory or dependency map. Generate missing plans and reusable execution/verification recipes from the project goals and observed working practices. A generated recipe remains unverified until exercised; preserve its inputs, environment and evidence when it runs.

### Living documents and coherence maintenance

A living document has a purpose, persistent context, source/dependency references, a maintenance policy, and the ability to initiate upkeep or raise unresolved questions. Its maintainer reasons about what needs to change for the document to remain useful: stale statements, inconsistencies, missing evidence, broken links, duplicated explanations, and material that should be consolidated or moved. Keep authored maintenance in an existing scoped PR or a new ordinary PR on the existing watcher/session substrate; a permanently running agent per file is unnecessary. This is a concrete first slice of [[plan-984dfeb]], including self-maintenance, while preserving its broader negotiation design.

Use editable Markdown plus lightweight metadata or sidecars, retaining existing file paths and human edits. Track document identity, relevant sections/claims, source revisions or evidence references, related documents, last checked state, pending maintenance, and policy for applying changes. Initial onboarding should discover likely relationships from links, citations, and repeated claims, then record the useful ones; keeping docs current cannot depend on a human exhaustively declaring every relationship. Periodic coherence sweeps catch missing links and changes made outside pm.

Changes to source data, accepted results, methods, code interfaces, plan decisions, or adopted child revisions schedule maintenance for affected documents. Coalesce a batch of related changes into one PR; reconcile current text against the sources, propagate supported corrections, repair links, and record what changed and why. Preserve existing documents' purposes: a methods section, study register, README, and paper need coherent claims rather than identical prose. Readers see stale, contested, and pending-update state until reconciliation completes. A last-checked revision establishes freshness relative to those sources, not scientific validity; required checks remain part of the PR's review/QA, using D6 methods where appropriate.

Contradictory sources produce a visible question or investigation, not an invented resolution. A corrected or withdrawn finding must update or flag its downstream summaries and conclusions, including uncertainty and scope. Preserve historical result snapshots and dated digests; issue linked corrections instead of rewriting the historical record. Across repositories, distinguish latest child findings from the revision the parent has actually adopted. Maintenance must not silently advance an accepted pin.

Routine maintenance follows the document's configured policy and can run unattended. Respect author-owned passages and existing paper-integration instructions: apply permitted changes, prepare scoped patches where required, and keep pending disagreements visible without blocking unrelated work. Use stale-write detection and the existing mutation helpers to preserve concurrent edits. Bounded retries, deduplication, and change-impact tracking prevent documents repeatedly rewriting each other. A no-change sweep creates no new content churn, and housekeeping alone cannot perpetually reset the campaign's no-progress limit.

Radar consumes this maintained project context and records which revisions informed each triage. Missing/stale context triggers maintenance or a visibly provisional judgment. Relevant new findings can propose or file ordinary document-maintenance PRs through existing PM operations, and changed project conclusions can trigger reconsideration of affected live Radar syntheses. D10 does not depend on Radar ingestion; D7 consumes D10 and connects those two directions. Neither requires the full Mind/Sensorium migration.

For cosmic, the first concrete chain connects S10's authoritative result/method artifacts to its study plan, the study register, project overview, and relevant paper passages. For Omerta, connect child implementation/research state to child docs and parent summaries, respecting accepted revisions. A real change must result in supported document updates or an explicit unresolved/pending correction; merely refreshing a dashboard or appending a new summary does not satisfy this requirement.

### Sessions and model independence

PM needs to know how to start the selected agent in the right workspace with its instructions, model/provider settings and authority, and record where that session lives. Keep observability and human interaction through tmux. Agents and watcher prompts inspect sessions, interpret progress and recover interrupted work; autostart must not require hooks, transcript event parsing, idle detection or any other automatic inference of agent state. A finished turn or exited process does not establish a domain outcome.

Separate the agent harness/backend from model/provider/effort selection. The named harness targets are Claude, Codex, OMP, Grok, Muse, the DeepSeek harness, and OpenCode. These are delivery targets, not claims of current support or compatibility with every model. Running a DeepSeek model through the Claude harness is recorded as that combination; it does not establish support for the DeepSeek harness. Support project defaults and per-role overrides, preserving existing more-specific model choices. Resolve capabilities explicitly; unsupported combinations produce an actionable error rather than silently falling back to Claude or a hosted model. Provider-specific options remain in adapters, with recorded effective settings.

The complete role inventory comes from launch call sites, not just today's `SESSION_TYPES`: implementation; review; all QA planning/authoring/scenario/concretization/verification/finalization/regression roles; sign-off; merge; watcher and watcher review; plan creation/review/fix; guide; meta; discussion; literature/doc review; spec generation; mock generation; background checks; default chat; container and cluster/bridge sessions. Research and document work use the existing PR implementation/review/QA roles; Radar and panel sessions share the same launch interface.

Reuse the existing tmux and bridge surfaces for all seven harness targets. Backend-specific launch/setup instructions belong at that boundary; native event-stream or completion-detection support is not a prerequisite for integration. Preserve native resume/attachment where available without making cross-vendor conversation portability a requirement. Inventory each concrete harness implementation, version, supported model/provider endpoints and launch environments before claiming coverage; the product name alone does not identify an interchangeable adapter.

Prioritize controlled evaluation of open models: run the same pinned model on the same tasks through multiple compatible harnesses, and compare models within a fixed harness as a separate comparison. D4 supplies the selectable adapters and bounded comparison; D9 reuses them for sustained performance/cost optimization. Keep unsupported harness/model combinations visible. A harness that only supports a different model can be evaluated as a complete system, but that result cannot isolate a harness effect.

Backend coverage includes project instructions, workdir/context, executable and authentication setup, permissions, session identity, logs and human attachment. Translate backend-specific instructions through shared PM context while preserving project-authored guidance. D4 must demonstrate agent-driven autostart with hooks and automated agent-state detection disabled, including the Claude path; adding a Codex-specific detector does not satisfy this requirement.

### Watcher ownership and code cleanup

Participating agents advance PRs through shared PM operations and durable project records. Prompts allow implementation, review, QA and sign-off sessions to record a handoff and request the next existing stage within their authority. Watchers inspect work through tmux, reconcile missing handoffs or failed requests, maintain plans, and reason about priorities and progress. Exploratory research and authored plan changes remain ordinary PR work; routine observation and tool calls belong to that work rather than becoming new work units. Respect a PR waiting for human collaboration in implementation. Existing PM commands already let a PR file linked follow-up PRs; the sign-off prompt asks whether the result warrants such work or a plan revision.

Replace the programmatic autostart phase engine with agent-controlled execution. Keep useful CLI/TUI entry points, target visibility, shared data/tool operations, launch setup and the tmux substrate; migrate their meaning to agent requests and recorded actions. PM launches agents and executes explicit operations, while prompts carry workflow interpretation and recovery. Remove hook/idle/transcript-driven phase advancement and competing scheduler decisions from the migrated path. Durable records are authoritative rather than mirrors of a running TUI. GitHub contributes repository facts without overwriting an active workflow attempt. A simple timed watcher wake-up remains useful and requires no agent-state detector.

Centralize safe plan/registry mutations and shared verdict definitions. Preserve file-based, git-tracked canonical state as decided in [[plan-state]]. A plan edit and corresponding registry update need validation, a recoverable paired-write operation, and one coherent commit; filesystem rename alone cannot make two files atomic. Preserve unrelated working-tree edits and reject stale writes. Agents record revision/attempt-bound handoffs, requests and reasons through these operations. Reject stale updates and duplicate launches; preserve dependency constraints, configured spec/merge holds and approval freshness for every caller. A worker report does not grant additional authority. The initial scheduling prompts add structured entries and notes; D10 performs scoped prose maintenance through the document's edit/acceptance policy. Broader plan rewrites remain explicit scoped PR work with review.

This is the initial refactor boundary. Full Mind/Sensorium migration, a new database, generalized governance, and a wholesale UI rewrite are separate work. Successful delivery should remove duplicated behavior as well as add features.
