# Document evaluation and prompt improvement

Draft revision, October 20, 2026. Supersedes the previous text once accepted; intended home is pm/plans/plan-doc-eval.md.

Build and run a document-only improvement loop, then carry measured improvements into PM's existing planning prompts. This is the first bootstrap: generate documents, evaluate their quality, edit the generation prompt and repeat. Code execution benchmarks and full PM evaluation follow afterward.

## Experiment

Use the [collected corpus](../../experiments/plan-writing/sources.json) as known-good writing without manual quality curation. Automatically sample across sources, document types and lengths; keep duplicates and documents from the same project together when splitting development, validation and final evaluation sets.

Every case needs a natural prompt. Assemble each brief from the document's surrounding infrastructure, not from its body: the tracking issue or discussion thread that requested it, the process document or template it follows, the index entry that places it, the working group charter or study call it answers. Record the provenance of every brief. Do not reverse a brief out of the document itself; a brief written from the document trades leaking its content against telling the generator what to write, and no setting of that trade is trustworthy. Prepare continuation cases for every document as well: show the document up to a section boundary, ask for the next section, and hold the original next section as the reference. Documents with recoverable context therefore yield both a whole-document case and continuation cases; documents without it yield continuation cases only. The generator never sees the reference in either case type.

Include PM's own plans as natural-prompt cases. The recovered task conversations are the prompt; the existing plan file is the production baseline, not a known-good reference. Track the quality of regenerated plans against those originals across campaigns, together with fidelity to the human turns. Plans with recovered sessions come first; plans without located histories follow after good outputs rather than blocking the campaign.

Before calibrating judges, survey published quality rubrics for technical and design documents and derive a general, referenced set of quality dimensions with definitions and detection guidance. Place the concerns already identified, padding, premature implementation detail, poor progression and lost requirements, within that set rather than treating them as the whole measure. Preserve useful elaboration rather than requiring every sentence to repeat the input. Judge factual fidelity against the brief or prefix as well as readability. An improved draft may beat its reference; the reference preference assumption bootstraps evaluation rather than imposing a permanent ranking.

Judges are frontier models and JEV. Calibrate them blinded against known-good originals and initial generated drafts. Whole-document cases and continuation cases are separate tracks: scored, calibrated and reported apart, never pooled into one score or paired across tracks. Judges of continuation cases see the prefix. Randomize pair order and hide origin labels. Measure consistency and sensitivity to source identity, formatting, length and, for continuations, stylistic continuity with the prefix, which favors the original author. Open-source classifiers such as GLiClass, perplexity and other features that need inference-engine access are later candidates, outside the first PRs, and never assumed quality scores. Run the previously identified human-rated writing comparison as a separate calibration check; it does not replace the technical-document corpus or require new human labels.

Optimize reusable generation prompts on development cases. Whole-document natural-prompt cases are the mode that matches production and the track final selection is made on. Continuation cases reach a wider range of documents, but prompt changes learned from them may transfer less well to fresh plan generation, so whether they help at all is itself a question the campaign answers, through the two-population design below. The evaluator is fixed once the rubric and calibration PRs land; campaigns iterate on generation prompts, not on judges or rubric. Select on validation, and evaluate the selected prompt on untouched cases. Compare against the unchanged production prompt with repeated paired generations and an independent evaluation configuration withheld from the optimizer. Record disagreements instead of hiding them in a single score.

The optimizer is itself a prompt and needs deliberate design. Given a candidate prompt with its generations, scores and judge rationales on development cases, it must separate general guidance, which would help this prompt or any other planning prompt, from fixes that fit only the cases seen; name what in the current prompt probably hurt the scores; and return an edited prompt with that reasoning attached. Version the optimizer prompt with the campaign and keep its reasoning alongside each edit.

Maintain populations of candidate prompts rather than one running best. Use a genetic scheme: fitness is aggregate performance over many development cases, selection keeps the strongest candidates while preserving some diversity, variation comes from optimizer edits as mutation and from recombining sections of strong candidates as crossover. Evaluation is sparse and cumulative, since no prompt will be scored on every case: stored evaluations are never repeated, each generation adds a few new case evaluations per candidate, drawn from cases other than those its edit was derived from, and fitness is the mean of all evaluations the candidate has accumulated, with the evaluation count recorded beside it. Run two populations. The first is evaluated only on whole-document cases and never sees continuation scores. The second is evaluated on continuation cases as well. Cross-breeding between populations is allowed, but a candidate entering the first population is re-scored on whole-document cases alone. Compare the best of each population on whole-document validation and final cases; the difference is the measured benefit of continuations. Record lineage so a winning prompt's ancestry and the edits that produced it can be inspected. Population size and generation count are picked per campaign from the usage estimates described under operation. The diversity-preserving methods noted in plan-self-improve remain later options.

Test iterative generation alongside prompt optimization. An iterative generator drafts the document, scores the draft with an in-loop critic, finds the passages that fall short on particular rubric dimensions, revises them, and repeats for a fixed number of rounds, so it optimizes the quality measure directly while writing. Compare one-shot generation against iterative variants that use JEV as the critic and a frontier model as the critic. Score the draft after every round with the withheld evaluation configuration rather than the critic, so improvement on the critic that does not appear on the independent measure is visible as overfitting to the critic. Report quality by round and by critic, together with the usage each variant consumes.

## Operation and adoption

Reuse `experiments/plan-writing`. Reach generator, optimizer and judge models, including open/local models, through `claude-mixed` sessions, which route model choices to Anthropic, OpenRouter or local servers. Work that needs inference-engine access, such as logprobs or per-request token accounting, is deferred. Extract the current inline planning prompts into callable builders only as needed to evaluate the same text that production uses; avoid a general prompt-framework refactor.

Run unattended with checkpoint/resume and a panel decision at campaign checkpoints about whether further work is worthwhile; stop on sustained lack of improvement. This plan sets no compute limits. Each PR that runs models first estimates how much of the weekly subscription limits runs of different lengths would consume, and the run length is picked from that estimate before starting. No single run may use more than twenty percent of the weekly budget. Keep prompt versions, task inputs, briefs and their provenance, generated documents, scores, failures and resource use so a claimed gain can be inspected and reproduced.

First adoption targets are the plan-development and PR-breakdown prompts in `pm_core/cli/plan.py`. Test them on the recovered PM task conversations as well as the public corpus, and report each campaign's regenerated plans against the original plan files; missing histories for other plans do not block the campaign. Preserve user intent, required plan fields and dependency semantics. Further prompt families can use the same loop after this first adoption.

Success requires an actual campaign and at least one supported improvement to an existing production prompt, followed by fresh generation through its normal PM entry point, with a reported comparison of regenerated PM plans against their originals and of one-shot against iterative generation. If no candidate wins, retain the baseline and report that result; the adoption goal remains outstanding. Human review remains available, with no routine manual labeling or approval gate added to the experiment.

The next stage is [execution evaluation](../docs/planning-evaluation.md), starting with existing benchmark inputs and comparing direct execution without a separate plan, current planning and improved planning. It checks whether document-quality gains improve task outcomes. Full PM orchestration and the logged proposal/code/test cases extend that stage; none is a prerequisite here.
